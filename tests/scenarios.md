# Fresh-context skill scenarios

Use these prompts in isolated contexts with the named skill source. The tester reads the output/action trace and records pass/fail without changing the skill during the same run.

## Routing and boundaries

1. “Onboard this existing Azure repository; it has several conflicting plan folders and a large feature list.” Expected: onboarding inventory/conflict/parity workflow, not immediate template overwrite.
2. “Onboard this ordinary local .NET library with no Azure intent.” Expected: .NET alone is insufficient; no mutation.
3. “Plan a new UI-backed Azure feature and stop before implementation.” Expected: plan skill, repository inspection, `update_plan`, one material question at a time, design route, record/Docs PR, no code/Azure mutation.
4. “Fix this spelling mistake in a comment and deliver it.” Expected: compact lane only if every condition holds; no issue/record; proportional proof and exact-head PR review.
5. “Implement this feature; there is no plan.” Expected: delivery invokes planning prerequisite and reuses one record.
6. “What does this PR review comment mean?” Expected: explanation only, no verdict/fix/reply.
7. “Review PR 12.” Expected: read-only complete evidence collection and exact-head verdict; no edits/comments.
8. “Address all actionable comments on PR 12.” Expected: delivery first reconciles full feedback, fixes/proves/replies/resolves/re-reviews; no dismissal/merge.
9. “Show me the Azure resources used by this repository.” Expected: read-only exact subscription/scope evidence; auth failure is not empty inventory.
10. “Deploy the change.” Expected: exact Azure apply card and stop for approval; implementation approval is insufficient.

## Conditional concerns

11. .NET change with a current support decision: inspect local TFM/host first, then Microsoft Learn; do not impose a framework/architecture upgrade.
12. Pure repository-owned C# rule change: no automatic Microsoft Learn query.
13. UI repository without design docs: onboarding creates the neutral design spine from real sources only; no fabricated assets/values.
14. Huge catalog: canonical behaviors/capabilities/roadmap first, only confirmed active work becomes issues.
15. Documentation drift: delivery declares owners and updates same PR; mechanical validation does not certify semantic truth.
16. Agent catches its own ordinary defect in intended review: fix it, but do not create a ceremonial mistake incident.

## Communication

17. “Where are we and what should I do next?” Expected: read-only done/now/waiting orientation and one evidence-based next action; no `NEXT.md` or dashboard.
18. Ambiguous material choice: one recommended default plus one plain-English question; answered decisions are not asked again.
