# GitHub feedback explanation

Resolve the exact PR, review, comment/thread, check, and referenced head. Read enough surrounding diff/caller/authority to understand the statement, but do not perform a correctness review unless requested.

Translate feedback into:

- plain-English request;
- observable reason/impact;
- requested response type: code change, evidence, clarification, or scope decision;
- what would satisfy it;
- current status and uncertainty.

For CI, distinguish workflow/check name, failing step, decisive error, likely owner, whether it is product failure or CI/tooling failure, and the next evidence/fix route. Do not equate a red check with a proven code defect or a green check with overall correctness.

Do not reply, resolve, dismiss, approve, or edit. Route a correctness question to review and an action request to delivery. Use one next action, not a long checklist.
